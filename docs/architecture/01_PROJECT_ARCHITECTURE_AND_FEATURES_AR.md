## 1. الملخص التنفيذي والفلسفة الأساسية

### هوية المنصة

**Structo** (المعروف داخلياً بـ _Ousos_) هو **منصة SaaS متعددة المستأجرين لإدارة الشؤون المالية في قطاع البناء والتصميم الداخلي** تستهدف السوق المصري. تُمكّن المنصة شركات المقاولات، المكاتب الهندسية، والمهندسين المستقلين من:

- **التسجيل والانضمام** كشركة SaaS متعددة المستأجرين مع بوابات موافقة SuperAdmin.
- **إدارة مشاريع متعددة** مع تحديد الموقع الجغرافي، بيانات العميل، وتتبع الميزانية.
- **تشغيل دفتر أستاذ مالي متكامل** (حقن رأس المال ← العُهدة ← التسوية ← المُطابقة ← الإغلاق النهائي).
- **عرض دليل محفظة أعمال عام** لاكتساب العملاء وبناء الثقة.
- **استقبال إشعارات فورية** عبر SignalR + تكامل بريد OneSignal.

### هيكل تعدد المستأجرين

```
┌─────────────────────────────────────────────────────────┐
│                     طبقة SuperAdmin                      │
│  (إشراف شامل، بوابات الموافقة، إدارة المراجعات)         │
├──────────────────────┬──────────────────────────────────┤
│     المستأجر أ       │         المستأجر ب               │
│  ┌──────────────┐    │    ┌──────────────┐              │
│  │ مالك الشركة  │    │    │ مالك الشركة  │              │
│  │ محاسب        │    │    │ مهندسين...   │              │
│  │ مهندسين...   │    │    │ مشاريع...    │              │
│  │ مشاريع...    │    │    └──────────────┘              │
│  └──────────────┘    │                                  │
├──────────────────────┴──────────────────────────────────┤
│              EF Core Global Query Filters                │
│  .HasQueryFilter(e => TenantId == null || e.TenantId)    │
│  يُطبَّق على: المشاريع، المستخدمين، العُهدة النثرية،   │
│  التسويات، المعاملات المالية، صور الموقع، صناديق النقد،  │
│  بنود التسوية، الإشعارات، سجل الميزانية                 │
└─────────────────────────────────────────────────────────┘
```

كل كيان مرتبط بمستأجر يُنفذ واجهة `ITenantEntity` ويتم تصفيته تلقائياً عبر `StructoDbContext.CurrentTenantId`، الذي يقرأ من claim `tenantId` في JWT عبر `TenantContextAccessor`. مُعترض `SetTenantIdOnSave()` يُختم تلقائياً `TenantId` على كل كيان جديد. نقاط النهاية العامة (`/api/public/*`) تستدعي `.IgnoreQueryFilters()` صراحةً.

### المنصة التقنية

| الطبقة | التقنية |
|---|---|
| **واجهة API الخلفية** | ASP.NET Core 8، استضافة مبسطة (`Program.cs`) |

| **التحقق** | FluentValidation (خط أنابيب تحقق تلقائي) |

| **CSS** | TailwindCSS + رموز تصميم مخصصة |
| **النشر** | Docker + Railway (ربط PORT ديناميكي، TLS على الحافة) |

## 2. التفصيل الكامل للميزات

### الوحدة 1: المصادقة والتسجيل

| الميزة | نقطة النهاية | الوصف |
|---|---|---|
| تسجيل الدخول بالبريد/كلمة المرور | `POST /api/auth/login` | تحقق BCrypt، إصدار JWT + Refresh token، فحص المستأجر/التعليق |
| تسجيل الدخول بـ Google OAuth | `POST /api/google-auth/google-login` | إنشاء تلقائي لمستأجر + مالك إذا كان البريد جديد؛ دمج تلقائي للأسماء للموظفين المسجلين مسبقاً |
| تسجيل المستأجر | `POST /api/auth/register-tenant` | تقييم قوة كلمة المرور (≥3/5 معايير)، إنشاء مستأجر (بانتظار الموافقة) + مستخدم مالك |
| تجديد التوكن | `POST /api/auth/refresh` | تدفق صامت 401 ← تجديد ← إعادة المحاولة عبر JWT interceptor في Angular |
| بوابة اكتمال الملف الشخصي | استجابة تسجيل الدخول `isProfileComplete` | يفحص `ManualAddress` + `Latitude`/`Longitude` للشركة؛ `NationalId` + العنوان للمستقل |

### الوحدة 2: تعدد المستأجرين والاشتراك

| الميزة | نقطة النهاية | الوصف |
|---|---|---|
| عمليات CRUD للمستأجر | `POST/GET /api/tenants` | SuperAdmin ينشئ/يعرض جميع المستأجرين مع بحث عن المالك |
| توفير المستأجر | `POST /api/tenants/{id}/provision` | تفعيل المستأجر، تعيين `MaxActiveProjects` حسب الخطة، الموافقة التلقائية على المالك، إرسال بريد التفعيل |
| تعليق/إلغاء تعليق المستأجر | `POST /api/tenants/{id}/toggle-status` | التبديل بين `Active` ↔ `Suspended`؛ المستأجرون المعلقون يُحظر عليهم تسجيل الدخول |
| الملف الشخصي للمستأجر | `GET/PUT /api/tenant-profile` | يحدّث مالك الشركة معلومات الشركة، روابط الشعار/البانر، الموقع الجغرافي |
| حصة المستأجر | `GET /api/tenant-profile/quota` | يُرجع `usedProjects` / `allowedProjects` لتنفيذ الحصة |
| ملف تدقيق المستأجر | `GET /api/superadmin/tenants/{id}/profile` | SuperAdmin فقط: عدد المشاريع، عدد المستخدمين، التخزين المُقدَّر، التقييم العام |

| قياسي | 10 | التوفير / الموافقة |

### الوحدة 3: إدارة المشاريع

| الميزة | نقطة النهاية | الوصف |
|---|---|---|
| إنشاء مشروع | `POST /api/projects` | فرض الحصة ← `PendingActivation` إذا تجاوزت؛ تنقية HTML؛ تحليل وصف JSON القديم |
| تحديث مشروع | `PUT /api/projects/{id}` | فحص ملكية المستأجر؛ مشاريع `PendingActivation` محظورة لغير SuperAdmin |
| عرض المشاريع | `GET /api/projects` | SuperAdmin يرى الكل (مع فلتر `tenantId` اختياري)؛ الآخرون يرون مستأجرهم فقط |
| الحصول على مشروع واحد | `GET /api/projects/{id}` | `PendingActivation` ← 403 لغير SuperAdmin؛ SuperAdmin يحصل على وصف فارغ |
| عرض العميل | `GET /api/projects/{id}/client-view` | لقطة مشروع عامة مع آخر 5 صور موقع (التقدم مُقدَّر بـ 45%) |
| مراجعة الميزانية | `POST /api/projects/{id}/budget-revision` | مالك/محاسب؛ ينشئ سجل `ProjectBudgetLog` مع رابط ملف BOQ |
| تاريخ الميزانية | `GET /api/projects/{id}/budget-history` | سجل زمني مرتب لجميع تغييرات الميزانية |

**خصائص المشروع:**
- الجغرافية: `Governorate` (المحافظة)، `CityOrZone` (المدينة/المنطقة)، `SiteAddress` (عنوان الموقع)
- العميل: `ClientName` (اسم العميل)، `ClientWhatsApp`
- التصنيف: `PropertyType` (سكني/إداري)، `Category` (فئة)، `IsPublicPortfolio` (محفظة عامة)
- دورة الحياة: `Status` (نشط ← تجميد مالي ← مُغلق ← بانتظار التفعيل)
- المراجعة: `PublicReviewToken`، `ClientRating` (1-5)، `ClientReviewNotes`، `IsReviewHidden`

### الوحدة 4: الدفتر المالي والخزينة

| الميزة | نقطة النهاية | الوصف |
|---|---|---|
| حقن رأس المال | `POST /api/projects/{id}/financialtransactions/inject-capital` | إنشاء/تحديث `ProjectCashPool` حسب نوع المصدر؛ إنشاء معاملة إيرادات |
| صناديق النقد | `GET /api/projects/{id}/financialtransactions/cash-pools` | يعرض جميع الصناديق لمشروع (إيداع عميل، رأسمال المالك، قرض خارجي) |
| معاملة يدوية | `POST /api/projects/{id}/financialtransactions` | إيرادات/مصروفات مع حماية تجاوز الميزانية (المالك يمكنه الإجبار عبر `ForceOverrun`) |
| قائمة المعاملات | `GET /api/projects/{id}/financialtransactions/mobile` | مُرقَّمة، مرتبة بالتاريخ، تحويل المنطقة الزمنية لمصر |
| تحديث معاملة | `PUT /api/projects/{id}/financialtransactions/{id}` | محظور للمعاملات التلقائية؛ تنظيف الإيصال القديم |
| حذف معاملة | `DELETE /api/projects/{id}/financialtransactions/{id}` | محظور للتلقائية (غير رأسمالية)؛ استعادة رصيد الصندوق تلقائياً لرأس المال |
| الصرف المباشر | `POST /api/projects/{id}/financialtransactions/direct-disbursement` | المالك/المحاسب يخصم من الصندوق ← ينشئ عُهدة نثرية (صادرة) + معاملة صرف مباشر |

**حماية التجميد المالي:** جميع نقاط النهاية المالية تفحص `project.Status != FinancialFreeze && != Closed`.

**حماية تجاوز الميزانية:**
```
إجمالي المصروفات + المبلغ الجديد > ميزانية المشروع
  ← إذا ForceOverrun && الدور == مالك ← السماح (يُعلَّم IsOverrun)
  ← وإلا ← إرجاع BUDGET_EXCEEDED
```

### الوحدة 5: إدارة عُهدة الموقع (العُهدة النثرية)

| الميزة | نقطة النهاية | الوصف |
|---|---|---|
| طلب عُهدة | `POST /api/projects/{id}/pettycash` | المهندس يقدم طلب (تعيين تلقائي لـ `IssuedToUserId` للمهندسين، حماية IDOR)؛ إشعار للمحاسب + المالك |
| الموافقة على العُهدة | `POST /api/projects/{id}/pettycash/{id}/approve` | خصم من صندوق النقد المختار؛ تسوية تلقائية لطلبات التعويض |
| رفض العُهدة | `POST /api/projects/{id}/pettycash/{id}/reject` | إضافة تعليقات الرفض |
| تسوية سريعة | `POST /api/projects/{id}/pettycash/{id}/settle` | تسوية مباشرة قديمة (المالك/المحاسب فقط)؛ إنشاء معاملة مصروفات |
| تحديث العُهدة | `PUT /api/projects/{id}/pettycash/{id}` | فقط للسجلات غير المُسوَّاة |
| حذف العُهدة | `DELETE /api/projects/{id}/pettycash/{id}` | استعادة رصيد الصندوق إذا كانت صادرة؛ حذف الإيصال من التخزين السحابي |

**دورة حياة العُهدة:**
```
قيد الانتظار ← [موافقة] ← صادرة ← [تسوية] ← بانتظار التسوية ← مُسوَّاة
                  ↘ [رفض] ← مرفوضة
```

### الوحدة 6: التسويات والتعويضات

| الميزة | نقطة النهاية | الوصف |
|---|---|---|
| إنشاء تسوية | `POST /api/projects/{id}/settlements` | بنود مع فواتير؛ وضع مسودة أو قيد الانتظار؛ تستبدل المسودة الموجودة؛ المالك يوافق تلقائياً |
| الموافقة على التسوية | `POST /api/projects/{id}/settlements/{id}/approve` | حساب `NetDifference = العُهدة - المصروف`؛ انظر مصفوفة المنطق أدناه |
| تأكيد الاسترداد | `POST /api/projects/{id}/settlements/{id}/confirm-refund` | المحاسب يؤكد استلام النقد المُعاد؛ استعادة الصندوق + الميزانية |
| رفض التسوية | `POST /api/projects/{id}/settlements/{id}/reject` | إعادة العُهدة لحالة `Issued` لإعادة التقديم |
| عرض التسويات | `GET /api/projects/{id}/settlements` | المهندسون يرون تسوياتهم فقط؛ المالك/المحاسب يرون الكل |

**مصفوفة منطق الموافقة على التسوية:**

| الحالة | تغيير الحالة | الإجراءات |
|---|---|---|
| `المصروف < العُهدة` (إنفاق أقل) | ← `ApprovedPendingRefund` | تسجيل المصروف كمصاريف؛ انتظار تأكيد الاسترداد |
| `المصروف == العُهدة` (تطابق تام) | ← `Approved` | تعليم العُهدة كمُسوَّاة؛ تسجيل المصروفات |
| `المصروف > العُهدة` (إنفاق زائد) | ← `Approved` | تعليم العُهدة كمُسوَّاة؛ تسجيل المصروفات؛ **إنشاء طلب عُهدة تعويض جديد** (قيد الانتظار، `IsReimbursement = true`) |

**منع الاحتساب المزدوج:** يتم تسجيل مصروفات `settlement.TotalAmount` مرة واحدة بالضبط أثناء `ApproveSettlementAsync`. يُنشئ `ConfirmRefundAsync` فقط معاملة `RefundToTreasury` للمبلغ المُعاد.

## 3. سيناريوهات عملية وأمثلة ملموسة

### السيناريو أ: دورة حياة كاملة للعُهدة-التسوية-التعويض

> **الأطراف:** م. أحمد (مهندس موقع)، أ. خالد (مالك الشركة/محاسب)

```
الخطوة 1: حقن رأس المال
  أ. خالد ← POST /inject-capital { amount: 500,000, sourceType: "ClientDeposit" }
  النتيجة: صندوق "ClientDeposit" ← إجمالي الحقن: 500 ألف، المتاح: 500 ألف
           تسجيل معاملة إيرادات.

الخطوة 2: طلب عُهدة
  م. أحمد ← POST /pettycash { amount: 250,000, reason: "مستلزمات سباكة" }
  النتيجة: عُهدة نثرية (قيد الانتظار، 250 ألف). إشعار ← المحاسب + المالك.

الخطوة 3: الموافقة على العُهدة
  أ. خالد ← POST /pettycash/{id}/approve { sourcePoolId: "pool-guid" }
  النتيجة: العُهدة (صادرة). المتاح في الصندوق: 250 ألف. إشعار ← م. أحمد.

الخطوة 4: تقديم التسوية (إنفاق زائد: صرف 270 ألف من عُهدة 250 ألف)
  م. أحمد ← POST /settlements {
    pettyCashId: "custody-guid",
    lines: [
      { category: "سباكة", amount: 150000, invoiceUrl: "..." },
      { category: "تشطيبات", amount: 120000, invoiceUrl: "..." }
    ]
  }
  النتيجة: تسوية (قيد الانتظار). إجمالي المبلغ: 270 ألف. صافي الفرق: -20 ألف.

الخطوة 5: الموافقة على التسوية
  أ. خالد ← POST /settlements/{id}/approve
  النتيجة:
    1. التسوية ← معتمدة.
    2. العُهدة ← مُسوَّاة (المصروف: 270 ألف، المُعاد: 0).
    3. معاملة مصروفات: 270 ألف مسجلة.
    4. عُهدة تعويض جديدة:
       { amount: 20 ألف, reason: "تعويض مصاريف زائدة...",
         status: "قيد الانتظار", isReimbursement: true }

الخطوة 6: الموافقة على التعويض
  أ. خالد ← POST /pettycash/{reimb-id}/approve { sourcePoolId: "pool-guid" }
  النتيجة: التعويض معلَّم كمُسوَّى (تسوية تلقائية لـ isReimbursement).
           خصم 20 ألف من الصندوق ← المتاح: 230 ألف.

الخطوة 7: إغلاق المشروع
  أ. خالد ← POST /projects/{id}/freeze
  النتيجة: الحالة ← تجميد مالي. إنشاء PublicReviewToken.
           حظر جميع العمليات المالية المستقبلية.

الخطوة 8: مراجعة العميل
  العميل يستلم رابط: /public/project-review/{token}
  يقدم تقييم: 4 نجوم + ملاحظات.
  النتيجة: إعادة حساب متوسط تقييم المستأجر.

الخطوة 9: الإغلاق النهائي
  أ. خالد ← POST /projects/{id}/final-closeout
  فحص المُطابقة ينجح ← الحالة ← مُغلق. IsActive = false.
```

### السيناريو ب: تدفق الإنفاق الأقل والاسترداد

```
العُهدة: 100 ألف | المصروف: 70 ألف | المُعاد: 30 ألف
```

SuperAdmin **محظور صراحةً** من الوصول لأي سجلات مالية داخلية عبر `throw new UnauthorizedAccessException("SuperAdmin is strictly blocked from accessing internal financial records.")` في:
- `FinancialTransactionService` (جميع الدوال)
- `PettyCashService` (جميع الدوال)
- `SettlementService` (جميع الدوال)

هذا قرار تصميم مُتعمَّد: SuperAdmin يُدير البنية التحتية للمنصة ولكن يجب ألا يرى أبداً البيانات المالية لأي مستأجر.

## 5. هيكل الواجهة الأمامية

### هيكل مكونات Angular

```
app/
├── app.routes.ts            — تعريفات المسارات (تحميل كسول)
├── app.ts                   — المكون الجذري
├── core/
│   ├── guards/auth.guard.ts — حماية المسار حسب الدور
│   ├── interceptors/jwt.interceptor.ts — 401 صامت ← تجديد ← إعادة محاولة
│   ├── services/             — 18 خدمة قابلة للحقن
│   └── models/               — واجهات TypeScript
└── features/
    ├── auth/                 — التسجيل
    ├── login/                — صفحة الدخول
    ├── landing-page/         — الصفحة الرئيسية العامة
    ├── public/               — مراجعة المشروع (مجهول)
    └── dashboard/
        ├── dashboard-layout.component.ts — هيكل الشريط الجانبي + التوجيه
        ├── overview/         — تحليلات SuperAdmin
        ├── projects/         — قائمة المشاريع + التفاصيل
        ├── financials/       — واجهة الدفتر المالي
        ├── tenants/          — إدارة المستأجرين (SuperAdmin)
        └── pending-users/    — قائمة انتظار الموافقة على المستخدمين
```

### الأنماط الرئيسية في الواجهة الأمامية

1. **إدارة الحالة بالـ Signals:** `AuthService.currentUser` إشارة قابلة للكتابة؛ `isAuthenticated` إشارة محسوبة.
2. **JWT Interceptor:** يُرفق Bearer token لجميع طلبات API؛ يعالج 401 بتجديد مُرتَّب (يمنع تجديدات متعددة متزامنة).
3. **حراس مبنيين على الأدوار:** `authGuard` يفحص مصفوفة `route.data.roles`؛ يُعيد توجيه المستخدمين غير المُصرَّح لهم للصفحات الافتراضية.
4. **DashboardRedirectComponent:** يوجه `/dashboard` إلى `/dashboard/overview` لـ SuperAdmin، `/dashboard/financials` للآخرين.
